결론: 현재 UI는 기능 누락이 아니라 시각 언어와 배치 계약의 실패다. 이전 보고서는 “패널 없음”, “아이콘 우선”, “공유 컴포넌트”를 선언했지만 버튼 면, 텍스트 CTA, 점수 이해 순서, 정보 표면, 좌표와 간격을 닫지 않았다.

다음 수정은 라이브 수직 점수축을 폐기하고, 행동은 아이콘 버튼으로 통일하며, 흰 면은 읽어야 하는 정보에만 쓴다. 특히 특수 공 설명은 큐에 붙은 흰 정보 카드로 바꾼다. 모든 화면은 8px 간격 단위와 하나의 정렬 소유자만 사용한다.

증거 기준 AS-IS ↔ TO-BE 이전 보고서 실패 확정 수정 원칙 공유 시스템 화면별 사양 추가 AS-IS 구현 순서 수용 기준

2. 이전 refinement 보고서가 실패한 지점

문제는 구현자가 방향을 어긴 것만이 아니다. 보고서가 “좋은 말”을 선언한 뒤, 구현자가 판단해야 할 핵심 수치를 비워 두었다. 그 빈칸이 현재 화면의 흰 버튼, 텍스트 CTA, 뜬 설명, 어긋난 좌표로 채워졌다.

원래 선언보고서 안의 모순/누락현재 결과이번에 닫는 계약
“패널 없음”버튼 normal/hover/pressed의 면 색을 정하지 않았다. 흰 원형/사각 버튼이 TO-BE와 공유 SVG에 남았다.설정, 증감, 모드, 완료가 모두 흰 상자처럼 보인다.행동 normal은 투명. 흰 면은 정보 카드·설정 폼·확인 모달만 사용.
“아이콘 우선”아이콘 “우선”인지 아이콘 “전용”인지 불명확했다. 공유 SVG도 “다음/다시” 텍스트를 유지했다.플레이, 시작, 발사, 다음, 닫기가 큰 텍스트 버튼으로 구현됐다.동작 버튼의 visible text는 항상 빈 값. 접근성 이름과 tooltip은 유지.
“0–100 고정 수직축”완전한 범위를 보여 주는 것을 이해 가능성과 동일시했다. 목표 9–13 같은 좁은 구간과 R/G 색의 점수 역할을 읽는 순서를 정의하지 않았다.왼쪽 막대가 화면을 차지하지만 페인트 점수, 실제 칠한 면적, R/G 가중치의 관계를 설명하지 못한다.AIM의 라이브 수직축을 폐기하고, 목표·면적·색 기여도 중 무엇을 먼저 읽을지 세 안으로 비교한다. 전체 범위 축은 결과에서만 사용한다.
“공 설명 한 곳”보고서 데모는 어두운 tooltip 박스를 썼지만, shared component surface와 padding을 잠그지 않았다.특수 공 설명이 하늘 위 투명 텍스트로 떠서 정보인지 배경인지 불명확하다.큐 아래에 흰 BallDetailCard. 296px 폭, 16px padding, queue 우측선과 동일 정렬.
“공유 컴포넌트”컴포넌트 내부 padding과 화면 외부 gap의 소유자를 나누지 않았다.44/48/52/56/58/62px 크기가 혼재하고, 중심선과 edge가 화면마다 다르다.컴포넌트는 내부 치수만, HudRootLayout/screen owner는 좌표만 소유. 8px grid와 두 hit-target 크기만 사용.
“compact density”축소 비율만 있고 정보 우선순위와 재배치 계약이 없다.640×360에서 거대한 CTA와 수직축이 월드를 압박하고 설정은 스크롤 상태를 설명하지 않는다.compact는 별도 좌표 sheet. 행동은 40/48px, score UI는 선택한 위계를 유지하되 내용에 맞춰 축소하고 정보 카드는 280px 이내로 제한한다.
“PASS” 판정이 틀린 이유

2026-08-21 보고서는 clipping, 중복 tooltip, 누락 glyph 같은 기계적 결함을 제거한 사실을 사람의 이해와 시각 완성도로 확장했다. 캡처가 “깨지지 않음”은 증명했지만 “읽힘, 정렬됨, 좋아 보임”은 증명하지 않았다. 이번 보고서는 그 둘을 분리한다.

3. 사용자 피드백을 반영한 확정 원칙

LOCK 01

행동은 아이콘만

Play, Start, Fire, Finish, Back, Resume, Retry, Next, Close 등 동사는 버튼 안에 쓰지 않는다. 버튼은 실제 아이콘을 사용하고 localized accessibility name과 tooltip을 제공한다.

LOCK 02

흰 버튼 면 제거

routine action의 normal state는 투명이다. hover/pressed/focus에만 비흰색 피드백을 준다. 한 화면의 주요 행동 하나만 파란 원형 면을 가진다.

LOCK 03

흰 면은 정보에 사용

특수 공 설명, 설정 폼, 파괴적 행동 확인처럼 “읽고 판단해야 하는 내용”만 흰 정보 면을 쓴다. 정보 면은 hover/pressed 효과가 없어 버튼으로 오인되지 않는다.

LOCK 04

AIM 수직 점수축 폐기

AIM에는 0–100 수직 막대를 표시하지 않는다. 현재 점수, 목표 구간, 실제 칠한 면적, R/G 면적·가중치는 선택한 위계 안에서 서로 다른 의미로 읽혀야 한다.

LOCK 05

내부/외부 정렬 분리

컴포넌트는 icon centering과 padding만 소유한다. 화면 layout owner만 좌표, safe margin, group gap을 소유한다. screen script에서 자식의 임의 offset을 추가하지 않는다.

LOCK 06

값은 텍스트 예외

stage number, angle/power 값, timer, score 같은 데이터는 텍스트로 남는다. 버튼의 동작명만 제거한다. 정보 텍스트와 클릭 면을 한 덩어리로 만들지 않는다.

아이콘 전용의 접근성 보완

모든 action은 실제 아이콘 asset과 localized accessibility_name을 가진다. 일반 화면은 같은 문구의 tooltip을 사용한다. Main Menu는 tooltip 대신 아이콘 오른쪽의 label reveal을 hover와 keyboard focus에 동일하게 사용하며 둘을 중복 표시하지 않는다. 아이콘 의미를 색 하나에만 의존하지 않는다.

4.3 흰 정보 면 사용 규칙

허용: BallDetailCard

특수 공의 순서, 종류, 색 역할, 행동을 읽는 카드. warm white 96%, navy text, 14px radius, 16px padding, queue에 직접 부착.

허용: Settings/Confirmation

여러 값을 읽고 바꾸는 설정 sheet와 파괴적 행동 확인 modal. 한 화면에 한 containment level만 둔다.

금지: routine action

설정 gear, +/- stepper, Finish, camera mode, Back, Return, secondary result action의 normal state에 흰 면을 쓰지 않는다.

4.4 AIM ScoreStatus 후보와 ScoreScale 역할 분리

ScoreStatus — AIM 공통 계약

  • 필수 값은 페인트 점수·목표 구간, 칠한 면적, 빨강/초록 면적과 weight, 두 색 필수 여부다.
  • 표시 순서는 04 AIM의 세 안처럼 목표 우선, 면적 우선, 기여도 우선으로 달라질 수 있다. 현재 권장은 목표 우선이다.
  • 페인트 점수는 R% × R weight + G% × G weight. 칠한 면적은 가중치와 무관하게 R% + G%.
  • 가중치 copy는 더함 +1, 뺌 −1, 점수 제외 0으로 stage data에 맞춰 바꾼다.
  • 흰 card와 0/25/50/75/100 수직 track을 사용하지 않는다. 배경 대비가 필요하면 좌측 edge scrim만 사용한다.
  • standard x48, compact x12의 safe edge를 유지하고 내용 변화로 block 폭과 baseline이 움직이지 않게 한다.
  • 음수와 100 초과 값을 clamp하지 않고 부호를 그대로 표시한다.

기존 ScoreScale — 결과 전용

  • 가로 result summary preset만 유지한다. 라이브 vertical preset과 독립 Briefing preset은 제거한다.
  • 현재값과 목표 구간 label을 track 위에 직접 표시한다.
  • 좁은 target band는 최소 2px 표시 + 별도 label/leader로 의미를 보존한다.
  • Stage Select + Briefing은 scale 대신 목표·R/G 가중치·공 수·필수 공을 terrain 위 한 줄 rule summary로 표시한다.

01

Main Menu

기본 상태는 icon-only로 유지한다. 현재 가리키거나 focus한 action의 이름만 아이콘 오른쪽에 순서대로 드러나게 하며, 제목 아래 meta tagline은 두지 않는다.

정확한 수정

  • 제목은 “페인트 마운틴”만 표시한다. 설명, slogan, “산을 칠하고…” 같은 meta copy는 0개.
  • 기본 상태에는 Play/Stage/Settings/Quit icon만 보인다. hover/focus한 한 항목만 아이콘 오른쪽에 localized action label을 표시한다.
  • 아이콘 중심은 고정한다. label clip 폭 0→실제 폭, x −8→0, opacity 0→1을 140ms에 실행하고 text는 40ms 뒤에 들어온다.
  • 이전 label은 80ms에 닫는다. reduced motion에서는 지연과 이동 없이 즉시 전환한다.

정렬·입력 계약

  • 1280: title/action rail x56, item gap 12. reveal label은 icon 우측 12px, center y 일치.
  • 640: title x12/y10, action rail은 사용 가능한 세로 공간에 유지하며 label이 viewport 밖으로 잘리지 않는다.
  • hover 영역은 icon과 펼쳐진 label 사이를 하나로 처리해 포인터 이동 중 접히지 않게 한다.
  • keyboard focus도 동일 reveal을 사용하고 접근성 이름은 animation 상태와 무관하게 항상 존재한다.

02

Stage Select + Briefing

두 화면을 하나로 합친다. 선택한 stage의 실제 하늘·땅·지형을 바로 보여 주고, stage 규칙과 공 queue를 같은 화면에서 확인한 뒤 AIM으로 들어간다.

정확한 수정

  • 흰 빈 배경과 별도 Briefing route를 제거한다. 선택 stage의 실제 sky, ground, terrain, dressing을 같은 renderer로 표시한다.
  • terrain 양옆의 투명 </> icon, rail node click, rail horizontal drag 세 입력이 같은 selection action을 호출한다.
  • rule summary는 “목표 · 빨강/초록 가중치 · 공 수 · 필수 특수 공”, 우상단은 실제 queue 순서로 표시한다.
  • 우하단 파란 aim icon은 선택된 stage artifact가 준비된 경우에만 활성화하고 바로 AIM으로 진입한다.

정렬·성능 계약

  • terrain arrow center x56/1224, y360. rail x24..1256, bottom safe 24, visible node gap은 균등 분배한다.
  • rail은 전폭이지만 30개를 억지로 압축하지 않는다. 01–10 단위의 연속 window를 보여 주고 drag 시 선택 stage가 가능한 한 중앙에 온다.

1 · 목표 우선“0.0, 목표는 9–13, 9.0 부족”샷 계획과 clear 판정을 가장 빨리 연결한다. 목표 구간·현재값·overflow를 한 시선에 처리한다.작은 viewport에서는 rail 눈금을 0/current/target 세 지점만 남겨야 한다.
2 · 면적 우선“현재 0.0% 칠했다”실제 산이 얼마나 칠해졌는지 가장 직관적이다. 점수와 물리 면적의 차이를 학습시키기 쉽다.stage 목표가 면적 자체가 아닐 때 score 판단이 한 박자 늦다. 0% rail은 반드시 중립색 빈 track이어야 한다.
3 · 기여도 우선“빨강/초록이 각각 점수에 얼마를 더한다”+1/−1/0 weight, 음수 점수, 100 초과 점수까지 오해 없이 설명한다.산술 기호가 많아 반복 플레이에서는 과하다. 규칙이 복잡한 stage나 학습 단계에 적합하다.

고정 범위

  • 왼쪽 score 영역만 교체한다. mountain, cannon, trajectory, queue, settings, timer, ball count, angle/fire/power의 위치·크기·색은 그대로 둔다.
  • 흰 card나 button-like surface를 만들지 않는다. 배경 대비가 부족할 때만 좌측 edge에서 투명해지는 navy scrim을 사용한다.
  • 선택 전까지 세 안 모두 탐색안이며 canonical design spec을 바꾸지 않는다.

공통 의미·상태 계약

  • “칠한 면적”은 항상 R%+G%. “페인트 점수”는 R%×weight + G%×weight이다.
  • 빨강은 splat, 초록은 circle을 유지하고 weight는 더함 +1, 뺌 −1, 점수 제외 0으로 표시한다.
  • 음수와 100 초과 score를 clamp하지 않는다. 양 색 필수 조건은 별도 badge/문구로 남긴다.
  • 값이 변할 때 숫자만 갱신하고 block의 폭과 baseline은 움직이지 않는다.

“겹치지 않는다”만으로 PASS 처리하지 않는다. 화면별 AS-IS와 동일 viewport의 TO-BE를 나란히 놓고, 위 수치와 사람이 읽는 순서를 모두 검수해야 한다. 마지막 결과에는 버튼 면, score 이해, 특수 공 card, 내부/외부 정렬을 각각 별도 판정한다.

참조한 외부 기준

  • Nintendo · Splatoon 3 gameplay — 색과 실제 territory 상태를 직접 연결하는 paint feedback의 참고.
  • FuturLab · PowerWash Simulator progress — 겨냥한 표면의 진행률과 percentage를 즉시 표시하는 기준.
  • PlayStation · Returnal UX — 즉시 필요한 정보와 주변부 HUD를 분리하는 gameplay-first 원칙.
  • Google · Bullet chart — actual value와 target band를 한 축에서 비교하는 AIM 1안의 근거.
  • W3C · Use of Color — 색 이외의 shape, label, sign을 함께 쓰는 기준.
  • W3C · Target Size (Enhanced) — 자주 쓰는 custom target의 44×44 기준을 참고했다.
  • W3C · Content on Hover or Focus — 특수 공 card의 dismiss/hover/persistence 계약에 반영했다.
  • W3C · WCAG 2.2 focus additions — 2px perimeter와 focus 가시성의 근거로 사용했다.
  • Xbox Accessibility Guideline 113 · UI focus — game UI focus가 분명해야 한다는 기준을 적용했다.
  • Xbox Accessibility Guideline 114 · UI context — icon-only action에도 사전 맥락과 consistent labeling이 필요하다는 제한을 반영했다.
  • Xbox Accessibility Guideline 102 · Contrast — 월드 위 텍스트와 정보 면의 대비 필요성을 반영했다.
  • Xbox Accessibility Guideline 103 · Use of Color — label과 shape로 색 의미를 보강했다.
  • Godot stable · Custom GUI controls — minimum size와 focus drawing 계약의 구현 근거.
  • Godot · Using Containers — container가 자식 layout을 소유한다는 책임 경계의 참고. 구현 시 프로젝트 고정 Godot 4.7.1 문서와 다시 대조한다.
